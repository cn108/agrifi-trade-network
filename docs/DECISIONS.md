# Decisions

Newest last. Format: decision — reasoning.

1. **Modular Django monolith, PostgreSQL authoritative.** Matches the spec; SQLite only for fast tests and the mobile cache.
2. **JWT via Simple JWT, JTI-only revocation, short access (5 min) / 7-day rotating refresh.** Shared by Angular and MAUI; browser refresh token in HttpOnly cookie, MAUI in platform secure storage.
3. **Idempotency as a separate record, record-first insert.** Lets replays survive later edits; the unique `(owner, scope, key)` constraint is the authority; only that violation is treated as a replay.
4. **Idempotency resource reference is type+UUID, not an FK.** Keeps the component reusable; deletion protection is a `pre_delete` guard (bypassable by raw SQL).
5. **Idempotency replay records have a one-year retention window.** They are eligible for purge 365 days after creation; clients must not depend on replay responses beyond this window.
6. **Stock = append-only `StockMovement` ledger; balances always derived.** One consistent source of truth, auditable, no drift between competing counters. Model/queryset guards are complemented by PostgreSQL UPDATE/DELETE triggers.
7. **Two stock pools via movement types** (batch free pool, listing pool) instead of a stored allocation table; avoids a second balance to keep in sync.
8. **Reservations are separate rows, not movements.** They are temporary and reversible; on-hand only changes when consumed (SALE).
9. **Expired pending reservations stop counting at read time**; a periodic command only marks them for audit. Confirmed-order reservations have no expiry and stay committed until shipment, cancellation resolution, or consumption.
10. **Stock lock order listing -> batch (for allocate/deallocate) or reservation (for hold/commit/consume)** with `select_for_update()`, always inside `transaction.atomic()`. Batch review takes only the batch lock. Multi-listing operations sort by listing UUID.
11. **Allocation requires same seller, category and unit as the batch;** sale draws FIFO from allocated batches for traceability.
12. **Accepted batches are immutable;** edits only while `submitted`. Acceptance requires an active category.
13. **Buyers cannot see raw stock endpoints.** Checkout reports insufficient availability; a buyer-facing availability field can be added to the Angular marketplace surface in Phase 5.
14. **Open (assumed, reversible): unverified farmers may create listings.** Revisit when the verification workflow is built.
15. **Standalone PostgreSQL test compose file** runs the suite locally without requiring production `.env` values; CI runs the same suite on PostgreSQL 16.
16. **Order confirmation commits, shipment consumes.** Pending holds expire; seller confirmation clears their expiry and reserves those units indefinitely until dispatch. Shipping posts FIFO sale movements. This prevents a confirmed order's stock becoming available again from a background expiry sweep.
17. **Order checkout is one seller per order.** Prices/totals are server-calculated; item snapshots are immutable. Rejections roll back the idempotency record, order, reservations and history together.
18. **Dispute resolution does not process a refund.** Pre-shipment buyer-favoured outcomes release committed stock and cancel the order; after shipment, the order is terminal `dispute_resolved`. A simulated monetary remedy is deferred to Phase 4.
19. **Standalone PostgreSQL test compose file** (`docker-compose.test.yml`) uses an ephemeral in-memory PG16 data directory and test-only credentials, avoiding production `.env` requirements.
20. **Finance chart is explicitly simulated.** Payment debits simulated payment clearing and credits seller payable; settlement debits payable and credits simulated payout clearing; refunds debit payable before settlement or seller receivable after settlement. These are internal records and do not imply custody, an escrow arrangement or a real transfer.
21. **Confirmed shipment requires a simulated successful payment record.** This is an application workflow gate only; the payment record has no provider reference or real-money side effect.
22. **Finance event records and posted journals are append-only.** Corrective postings use opposite debit/credit reversal lines. PostgreSQL deferred triggers check the final journal line sums and currency consistency on commit.
23. **Refund eligibility is bounded by dispute outcome and paid amount.** Only a buyer-favoured dispute enables refund; serialized payment/order locks enforce aggregate refund caps.
24. **Build the browser dashboard in a separate Angular workspace at `web/`.** Keep the existing React/Vite project intact as legacy material; this avoids silently extending or destroying the non-target frontend while allowing phased Angular delivery.
25. **Browser refresh credentials use HttpOnly cookies; access tokens remain in memory.** Cookie transport reduces refresh-token exposure to script, while CSRF-protected state-changing requests and exact CORS origins mitigate ambient-cookie request risks. Do not persist bearer credentials in browser storage.
26. **Angular workflows call the existing versioned API rather than reproducing business rules.** The server remains authoritative for identities, prices, totals, stock availability, role permissions, order transitions and simulated-finance eligibility.
27. **MAUI harvest capture persists locally before confirming success.** Each SQLite draft retains one `client_sync_id` through retries, while active categories are cached only to support offline data entry; the API still validates and accepts every batch.
28. **MAUI uses platform `SecureStorage` for JWTs and SQLite only for the durable outbox/cache.** Access and refresh credentials are not stored in ordinary preferences or the outbox database.
29. **Each MAUI outbox row is scoped to the authenticated user ID.** A device may be used by multiple farmer accounts; local drafts must only be displayed and synchronized while the owning account is active.

30. **Buyer-visible availability is derived from the stock ledger on read.** Listings expose read-only `available_quantity` (on-hand minus unexpired reservations, floored at 0, 3 dp). It is indicative; checkout reservation remains the authority, so no balance is stored.
31. **Liveness and readiness are separate.** `/healthz/` never touches dependencies; `/readyz/` checks the database and returns a generic 503 while logging details server-side. Logs are JSON to stdout and must never include credentials or request bodies.
32. **A rejected harvest batch is immutable history; a correction is a new batch linked by `resubmission_of`.** The link is a OneToOne (one correction per rejected batch, enforced by the DB), the create path locks the original and returns 409 on a second correction, and the idempotency fingerprint includes the original. A correction needs a NEW `client_sync_id`; reusing the rejected batch's key conflicts. Corrections create no stock until approved.
33. **Listing availability uses subquery annotations, not per-row ledger queries.** `annotate_listing_stock` shares the ledger and reservation-expiry rules with `listing_stock`; the serializer falls back to the service when annotations are absent. Reservation/checkout still validate under `select_for_update`.
34. **MAUI sync logic lives in a UI-free `net10.0` Core library behind small interfaces** (`ISecureStore`, `IAppSettings`, `IHarvestBatchApi`) so it is tested with xUnit against an in-process fake API and a real SQLite file. Rejected drafts are corrected via a new linked draft; failed drafts are edited under a new key; sent-but-unresolved pending drafts are locked. Sync passes are serialised and concurrent 401s share one refresh.
35. **MAUI JSON uses snake_case** (`JsonNamingPolicy.SnakeCaseLower`); the earlier camelCase default silently failed to bind API fields.

36. **Correlation IDs are middleware-owned.** `RequestIdMiddleware` accepts a sanitised inbound `X-Request-ID` (`^[A-Za-z0-9._-]{8,64}$`) or generates one, stores it in a contextvar, returns it, and includes it in JSON logs, error bodies and audit events. Query strings are never logged.
37. **One error envelope, legacy `detail` kept.** `{code, message, detail, request_id, fields?}`. Field validation errors live only under `fields`. Unexpected exceptions still propagate in tests; production uses the JSON `handler500` with a generic message.
38. **Throttle rates come from settings at request time and are disabled under `manage.py test`** (tests opt in with `override_settings`). The default locmem cache is per process, so multi-worker deployments must set `DJANGO_CACHE_DB_TABLE` and run `createcachetable` (or use a shared cache). Login is limited per IP and per hashed email.
39. **Registration no longer reveals whether an email exists.** An existing email gets the same 201 shape and a fabricated id, with equalised hashing time. Cost: a genuine owner re-registering gets no signal until email verification exists (not in scope).
40. **Audit is a single append-only `audit` app, extending (not replacing) domain histories** (`OrderStatusHistory`, `StockMovement`, `Journal`). Events are written in the same transaction as the change, so rollback removes them; metadata keys are allow-listed and scalar; emails are stored only as keyed hashes. Immutable in ORM and a PostgreSQL trigger, verified by the PostgreSQL 16 Compose suite on 2026-11-05.
41. **Finance reports are read-only DB aggregates over the immutable journal** (`GET /api/v1/finance/reports/`), per currency, labelled simulated, finance operator and ops admin only. No stored balances.
42. **Sync receipts are derived from `IdempotencyRecord`, not a new `SyncOperation` table (deliberate deviation from spec section 5).** `POST /sync/operations/` is an envelope (`operation_id`, `operation_type`, `schema_version`, `payload`) that delegates to the existing harvest-batch workflow, so validation, locks, audit and idempotency are shared; `GET /sync/operations/{id}/` returns the receipt. Only applied operations have receipts; rejected ones return the error envelope and are re-sent as new operations. `operation_id` is used as `client_sync_id`. The only offline operation type is `harvest_batch.create`; others are rejected with 400 until a real offline need exists.
43. **OpenAPI via drf-spectacular, optional at runtime.** `config/settings.py` enables it only if importable (`HAS_SPECTACULAR`); `agrifi/openapi.py` provides no-op decorators otherwise so the app and tests run without it. It is listed in `requirements.txt` and CI validates the schema with `--fail-on-warn`; `docs/openapi.yml` is the committed contract. `/api/v1/schema/` and `/api/v1/docs/` are open only when `DJANGO_DEBUG` is on (evaluated at import), otherwise ops-admin only. Viewsets guard `get_queryset` with `swagger_fake_view`. The local `.venv-openapi/` exists only because the sandbox blocks user-site pip installs.
44. **One shared idempotency-conflict response.** Reusing an idempotency key with a different payload now raises `IdempotencyKeyConflict` (409, `code=idempotency_conflict`) from `idempotency.replay_response`, used by harvest, allocation, order and finance replays. Found by the Django/MAUI contract tests: the previous raw `Response(409)` bypassed the error envelope (no `code`/`request_id`), so clients saw the raw body. Sync `operation_id` and `client_sync_id` are compared as UUIDs (letter case no longer matters). The contract fixtures in `contracts/` are shared by `backend/agrifi/sync/test_contract.py` and the MAUI tests; changing either side without the other fails a test.
45. **MAUI retry policy is persisted scheduling, not sleeping.** `SyncPolicy` (exponential backoff 5s base, 15 min cap, ±25% jitter, 8 retryable attempts) stamps `NextAttemptAtUtc` on the draft; sync skips drafts that are not due, so backoff survives restarts and never blocks the UI. Retryable: 5xx, 408, 429, network errors, timeouts. 401 neither backs off nor spends retry budget (sign-in problem). Other 4xx, including the 409 idempotency conflict, are permanent (`failed`). After the retry limit a draft is parked as `failed`; manual retry resets the budget and resends under the **same** operation ID, so the server dedupes. Cancellation propagates and keeps the draft queued.
46. **MAUI SQLite uses `sqlite-net-pcl` 1.11.285.** Upgrade Core and UI from 1.9.172 after NuGet reported a high-severity SQLitePCLRaw 2.1.2 advisory. The updated dependency graph passes the Core vulnerability check and all 47 Core tests; platform-wide scanning is still pending.
47. **Retention policy: keep audit and finance records for at least seven years; retain idempotency replay records for 365 days.** At seven years, audit and finance history is reviewed for lawful archival or deletion; immutable history is never edited to achieve retention. Idempotency records are purged by maintenance after 365 days, limiting the safe replay window to one year. The owner selected these periods on 2026-11-05; legal and accounting review is still required before deployment.
48. **Compose API health check uses `/readyz/`.** `/healthz/` remains process liveness, while `/readyz/` checks database connectivity and fails closed without exposing connection details. Compose should not report the API healthy when PostgreSQL is unreachable. This readiness probe is operational plumbing, not a substitute for monitoring/alert delivery.
49. **Angular UI refresh is presentation-only.** Use a shared harvest-green visual language, responsive layouts and controls, visible keyboard focus, and reduced-motion support across the dashboard, catalogue, and account entry surfaces. Preserve existing API workflows, labels that identify simulated finance, and backend authority for business rules.
50. **Android compile prerequisites are explicit.** The local MAUI Android build uses the Android SDK and Microsoft OpenJDK 21 via `ANDROID_HOME`, `ANDROID_SDK_ROOT`, and `JAVA_HOME`; constrain the build to `net10.0-android` on Windows and restore the Core project before and after the UI restore to protect Core assets. A successful compile may still report XA0033 for the current Microsoft JDK version string; APK output is the compile evidence, while emulator/device verification is tracked separately.
51. **MAUI startup XAML uses only supported semantic properties.** `SemanticProperties.LiveSetting` is not available in the MAUI SemanticProperties API and caused a XamlParseException on app startup. Remove that attribute from the message label; the visible message remains available without an unsupported setting. The corrected standalone Debug APK launches on the Android 15 API 35 emulator.

52. **MAUI JSON requests are buffered and API errors are rendered from structured fields.** Android's streaming JSON content used chunked transfer encoding, which Django's local WSGI development server rejected as malformed HTTP. Serialize JSON to a byte-array body with a known content length. User-facing API errors prefer the standard `message`, then legacy `detail` or field validation text, and use a short status fallback for non-JSON/HTML responses. This keeps emulator testing and developer WSGI deployments usable without exposing full server error pages.
